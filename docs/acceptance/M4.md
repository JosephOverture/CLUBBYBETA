# M4 — ticket commerce review

Local engineering gate, 2026-09-23. The previous catalogue gate was completed before commerce implementation began. Migration `004_ticket_commerce.sql` is now applied to persistent local development data and is immutable; future changes require a new migration.

Implemented: server-priced quotes and order snapshots; dated product tiers, included and separately priced drink entitlements, admission conditions, inclusive tax inputs, promotions, occurrence/tier capacity, staff blocks, bounded quantities, ten-minute holds and current seller/market readiness. Terms acceptance is persisted. An occurrence lock serializes all capacity changes and stock is read after acquiring it. Quote evaluation rolls back without reserving stock. Buyer/channel idempotency prevents duplicate orders and a single durable payment attempt serves both web and iOS.

Stripe integration uses the current Accounts v2 Merchant configuration and direct PaymentIntents, connected-account scoping, application fees, account onboarding/readiness synchronization, pinned API/SDK versions, exact raw-body signature verification, rotation overlap, an inbox and authoritative retrieval. Uncertain provider responses retain stock. Expiry reconciles/cancels provider intents; late success during cancellation is compensated. Amount, currency, seller, attempt and environment must match the immutable order. No client confirmation endpoint can grant a paid ticket. Native checkout remains disabled without configured Stripe and accepted commercial policy; live commerce remains disabled pending M8.

Fulfillment issues one opaque credential per admission and independent drink counts. Admission and refund commands share the occurrence lock. Staff access is scoped to the assigned venue/event; duplicate scans, replay, wrong events, inactive rights and outside-window admission have explicit outcomes. A reasoned manager override cannot bypass cancelled/refunded/disputed rights. Clients include native PaymentSheet, web Elements, booking recovery, terms display, individual QR display and staff camera scanning, with server confirmation and retry keys.

Refunds select explicit admission units, block rights while pending, release stock only on success and reverse exact allocated application fees independently. Cancellation/rescheduling is connected to real bookings and durable notifications. External Dashboard refunds require explicit rights allocation; original payment callbacks cannot clear financial review. Disputes, payout failures, provider balance transactions, actual fees and reconciliation discrepancies are persisted. Commerce and provider books are separate balanced, append-only journals, sealed after creation. Receipts, currency-separated statements, scoped support, confirmation resend and verified stuck-payment recovery are available. Financial records and support content are included in privacy exports; deletion obligations remain visible for the M7 retention/review workflow.

Review corrections: fixed a PostgreSQL trigger field-resolution error; normalized idempotent date snapshots; prevented out-of-order success from reopening a reviewed refund; handled Stripe balance events without object IDs and unrelated connected-account payments; preserved legal seller snapshots; sealed journals against later insertion; added the prototype's separately priced vouchers and exact partial-fee reversal. Source formatting was normalized for reviewability.

Evidence: `pnpm check` passes both typechecks, all 70 tests across six files, and API/worker builds. Real PostgreSQL tests cover last-seat and cross-tier races, promotions, checkout retries, provider timeout recovery, amount/currency/account validation, uncertain cancellation, free orders, guest claims, individual ticket issuance, scan/refund races, partial refunds, signed HTTP callbacks, cancellation impact, external refunds, sealed journals, accounting reconciliation, support/privacy/receipt scope, rollback-only quotes, staff blocks, fixed price snapshots, web-cookie/native recovery and drink add-ons. The real Stripe SDK is tested with an intercepted transport for account creation, payment scoping, exact amounts, refunds and fees. Web and iOS/Hermes bundles export successfully. Persistent local PostgreSQL migration/startup with API and worker passes. Production dependency audit reports zero advisories.

Local gate conclusion: M4 is complete and M5 may implement table reservations/deposits using these financial and inventory boundaries. This is not production or provider certification. User-directed account setup remains outstanding: Stripe-hosted sandbox scenarios, live commercial/tax policy, verified delivery, signed iOS camera/3DS/Apple Pay tests, actual reconciliation/payout evidence, and final deployment/device checks. Fiscal invoices are the legal seller's obligation; the implemented document is a booking receipt. Saved methods, transfers/wallets, final operational dashboards/retention and additional native markets remain assigned to M7 as planned.

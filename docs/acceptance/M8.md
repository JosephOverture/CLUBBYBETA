# M8 — local operational completion and release review

Reviewed 24 September 2026 after the M7 gate passed. Migration 019 is applied to persistent local development and is immutable. The user explicitly selected local preparation because hosting, payment, email and Apple accounts are not configured. This closes the local implementation gate; the external public-release gate remains open.

## Implemented and reviewed

API replicas now share PostgreSQL-backed request budgets and trust only configured proxy addresses. Deployed database connections require verified TLS without URL overrides. AWS object access supports workload IAM roles. Workers expose private liveness/readiness, independently renew heartbeats, report successful maintenance and renew external-job leases without reviving expired ownership. Administration provides safe operational counts and paginated job inspection; controlled replay requires recent authentication, a current generation and an audit reason. Sensitive payment/email/privacy recovery remains with its domain workflow.

The AWS reference stack provides isolated private API/worker/web tasks, managed PostgreSQL, private media, secret containers, HTTPS routing, WAF, logs, dashboard/alarms and environment-scoped GitHub deployment access. Services begin disabled. The deployment workflow checks CI for the exact revision, publishes digest-addressed images, checks migration success before rollout, verifies actual service adoption/public readiness and restores prior task definitions on failure. No database downgrade is attempted. Additive migration readiness supports overlapping compatible artifacts; the first upgrade from pre-M8 requires the documented maintenance window.

Production live-commerce configuration validates a reviewed, expiring manifest tied to the exact revision and origins. The template deliberately fails validation. Provider activation, market readiness, seller agreements and emergency sales pause remain independent gates. Container secret materialization, provider/key rotation and database restore are documented. Encryption overlap supports staged key changes; the maintenance command rewraps stored ciphertext atomically, preserves admission credentials/financial postings and aborts on corrupt data.

The exported website has a production static host with security headers, restricted SPA routes, source-map/hidden-file protection and optional Apple association delivery. EAS/native configuration enforces production origins and project identity; deep links validate origin and resource IDs. Public event pagination preserves PostgreSQL timestamp precision, and saved venues have paginated listing and an exact saved-state endpoint. OpenAPI reflects command status codes, header requirements and core purchase schemas. See [workstream traceability](workstreams.md) for the full W01–W24 mapping and explicit design choices.

Browser review exposed duplicate sibling React keys that could retain private account content after logout. Distinct component keys fixed the issue; a fresh sign-in/sign-out against the running backend removed all private account fields from both the accessibility tree and DOM, with no new duplicate-key errors. Saved-venue add/remove and persistent session behavior were also checked. Expo patches and the esbuild security override were updated and verified after the fix.

## Release obligations and verdict

M0–M8 are locally complete under the agreed preparation scope. `pnpm gate M8` checks the recorded evidence. `pnpm gate M8 --release` intentionally rejects the remaining external obligations in `phases.json`; the code does not convert local tests into production sign-off.

Docker is not installed on this Windows host, so Linux container builds/import checks are configured in CI but have not executed here. The workflows have not been pushed/run; AWS has not been provisioned. Provider integration tests use actual SDK transport contracts and controlled doubles, not connected Stripe/Resend/Apple accounts. Cloud alert delivery, IAM permissions, real point-in-time recovery/rollback, forecast peak load, signed iPhone/TestFlight journeys, final privacy/accessibility review and App Store submission remain required. Financial and retention policies need the responsible business owner's approval.

Follow [deployment](../runbooks/deployment.md), [operations](../runbooks/operations.md) and [the release journey matrix](../release/launch-verification.md) when those accounts are available. No finite local suite guarantees that deployment/device verification will require zero corrections; this report records what was actually implemented and checked without making that promise.

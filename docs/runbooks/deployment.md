# Deployment preparation

One API/database/worker system serves both the website and signed iOS client. `infra/aws` is a concrete AWS reference deployment, not an account that has already been provisioned. It creates an isolated two-AZ VPC, private Fargate API/worker/web tasks, HTTPS ALB and DNS/certificate validation, WAF request limiting, private RDS PostgreSQL 17, private S3 media, secret containers, ECR repositories, logs, alarms and an environment-scoped GitHub deployment role. Production uses two replicas and two NAT gateways; staging uses one replica and one NAT. These resources incur costs only if an operator applies the stack.

The user has requested local preparation and has no provider accounts configured. No Terraform apply, remote deployment, GitHub push, account creation, email subscription or live payment has been performed by this implementation task. Terraform validation and mocked plans verify structure, not account permissions or service delivery. Docker is unavailable on this Windows host; CI contains the Linux image builds and import smoke tests. Run those checks before publishing an artifact.

## First environment

1. Configure separate staging/production AWS accounts where possible, billing alerts, owner access and a protected operator role. Create an encrypted/versioned Terraform state bucket with restricted access and S3 locking. Configure the account-wide GitHub OIDC provider with audience `sts.amazonaws.com`. The environment role trusts only `P4210/Project-Clubby` and its exact GitHub environment; protect those environments and deployment branches with required reviewers.
2. Supply `region`, `environment`, hosted `zone_id`, `web_domain`, `api_domain`, exact `revision`, alert owner email and digest-qualified backend/web image references. Keep website and API under the same registrable HTTPS site, for example `clubby.example` and `api.clubby.example`, because web sessions use SameSite=Lax cookies. Use separate domains and data for staging. The initial infrastructure application uses `services_enabled=false`; images may be planned before being pushed because no tasks start.
3. Initialize the isolated state backend, inspect a saved Terraform plan and apply it through the owner's deployment process. Keep state encryption, versioning and access logs enabled. Never put credential values in `.tfvars`; the stack creates empty secret containers. Confirm the SNS subscription. RDS deletion and bucket destruction are explicitly protected.
4. From a private-network administrative session, create separate `clubby_migrator` and `clubby_app` database login roles with generated passwords using a secure database client. The migration role needs ownership/create access to `public`, database CREATE for the trusted `btree_gist` extension, and migration DDL; it must not be the RDS superuser. The runtime role needs schema USAGE, SELECT/INSERT/UPDATE/DELETE on application tables and sequence USAGE, but no role creation, database creation, schema CREATE or superuser privileges. Set default privileges for objects created by `clubby_migrator` so subsequent migrations grant runtime table/sequence access. The deployed migration CLI automatically revokes runtime INSERT/UPDATE/DELETE/TRUNCATE on `schema_migrations` and `platform_environment` for `clubby_app`; preserve these restrictions if using a differently named runtime role. Do not grant runtime ownership or permission to disable triggers; immutable financial/audit triggers remain active. Verify these grants in staging before enabling services.
5. Populate the application secret JSON with runtime `DATABASE_URL` and `APP_ENCRYPTION_KEY`; populate the migration secret with its separate `DATABASE_URL`. URLs require `sslmode=verify-full`; containers include the RDS CA bundle. Provider modes initially remain disabled. Add Resend, Stripe test and Apple credentials only as they are configured. `secret_keys` names the application secret's existing JSON keys; absent keys fail task startup. `additional_environment` is for nonsecret settings only. PEM fields listed in `scripts/container-entry.mjs` become mode-0600 temporary files and are removed from the child's environment. The nonroot backend needs ephemeral writable `/tmp` for these files; website containers use a read-only root filesystem.
6. Configure GitHub environment variables from Terraform outputs: `AWS_REGION`, `DEPLOY_ROLE_ARN`, `BACKEND_REPOSITORY`, `WEB_REPOSITORY`, `ECS_CLUSTER`, comma-separated `ECS_SUBNETS`, `ECS_SECURITY_GROUP`, `API_SERVICE`, `WORKER_SERVICE`, `WEB_SERVICE`, `MIGRATION_TASK`, `PUBLIC_API_URL`, `PUBLIC_WEB_URL`, `SERVICE_DESIRED_COUNT` (1 staging, 2 production), and the Apple team ID when available. Service names are `clubby-<environment>-api`, `-worker`, `-web`. No long-lived AWS access keys are required by CI.
7. Run the backend checks workflow on the exact revision. The manually dispatched deployment workflow requires its successful result, builds immutable digest-addressed images with provenance/SBOM, registers task revisions, runs the one-off migration task and checks its exit code before changing services. It verifies the expected task definitions and public HTTPS readiness and restores previous task definitions on rollout failure. Align the Terraform image/revision variables and `services_enabled=true` with the resulting deployment so a later plan does not undo it. Do not run concurrent Terraform/service deployments.
8. Verify sender-domain email delivery, sign in as the intended first administrator and run the container `bootstrap-admin` command with that verified email and an audit reason from an authorized one-off administrative task. It refuses to add another bootstrap administrator once one exists. Onboard real sellers, configure approved policies/markets, import reviewed catalogue records through the authenticated draft import workflow and publish after review. Development seed data is never applied to production.

## Commerce activation

Staging uses Stripe test keys, isolated sellers/webhooks and `LIVE_COMMERCE=false`. Production live commerce requires production, Stripe live, Resend with feedback signing, S3, encryption, and a release approval matching the exact Git revision and website/API origins. `docs/release/approval.template.json` is intentionally incomplete; a template is not evidence. Each required check needs a named reviewer and an HTTPS evidence reference. Approval timestamps must be valid, unexpired and no more than 30 days apart. This is a deployment-owner attestation, not automatic verification of an external report.

Populate `RELEASE_APPROVAL_JSON` in the application secret and include its name in `secret_keys`; set `RELEASE_REVISION` to the reviewed artifact, then enable `STRIPE_MODE=live` and `LIVE_COMMERCE=true`. On startup the container materializes the manifest and configuration validation refuses missing, mismatched, expired or incomplete approval. Seller policies, market approval, seller account capabilities and the emergency sales pause continue to be enforced independently. Existing entitlement/support operations remain available when new sales are paused.

The manifest checks cover real provider payments/refunds/disputes, approved seller terms/taxes/retention, security/privacy review, cloud restore/alert delivery, agreed capacity/outage rehearsal, browser journeys, signed iOS journeys and Apple/store metadata. A passing local suite does not satisfy those external checks. Follow [operations](operations.md) and [launch verification](../release/launch-verification.md) before enabling live commerce.

Production bundles contain the shared backend and production dependencies; frontend environment variables are embedded at build time and must contain public origins/identifiers only. Rebuild for a changed API origin. Never ship a development localhost URL or test account configuration to the App Store. The original root HTML prototype is excluded from the website container; it remains a design reference.

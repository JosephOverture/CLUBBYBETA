# Saved payment methods

Customers explicitly enable saved methods for a checkout, then separately opt in to saving the card used. Both choices default off. Saving uses Stripe `setup_future_usage=on_session`; Clubby has no unattended charge endpoint. Consent version, actor/channel/time and connected seller account are audited and fixed on the payment attempt. Resuming an existing checkout preserves those choices; changing them requires cancelling that unpaid checkout and creating another.

Each Clubby account has a separate Stripe Customer per connected seller account. Cards are not cloned between venues/organizers or exposed to another customer. Customer creation uses a durable mapping/idempotency key and recovers uncertain creation within Stripe's idempotency window. Beyond 23 hours, reconciliation searches by the mapping's exact provider metadata. Missing or ambiguous results require review; ordinary checkout remains available without saved methods. No card numbers, CVCs or raw payment details are stored in Clubby's database. List responses contain provider IDs and card brand, last four digits and expiry only.

Web Elements and iOS PaymentSheet receive a narrowly scoped CustomerSession for the same connected account and immutable payment customer. They redisplay only methods with `allow_redisplay=always`. Saving consent is collected in Clubby before the payment begins, so the provider's secondary save checkbox is disabled. After an authoritative successful payment, a durable `card.redisplay` job re-verifies payment/customer/usage and applies redisplay permission. A subsequent card removal takes precedence. A provider saving-setting discrepancy is recorded as `payment_attempts.card_save_status=review`; it never blocks fulfillment of an otherwise valid captured payment.

The account's Saved payment methods panel lists sellers and cards, supports pagination and authenticated removal. Removal checks ownership against Stripe before queueing and again before detaching. The durable `card.remove` job can recover from a lost response. Repeated removals are safe. A customer may also remove methods within Stripe's payment interface; the next list reads authoritative provider state.

Privacy integration calls `SavedMethodsService.eraseUser` outside database transactions to delete each connected-account Customer, then clears the local provider pointer and prevents delayed consent jobs from repopulating saved cards. Financial payment/refund records are retained according to the privacy/retention workflow; removing a saved card does not undo a payment.

Monitor dead `card.remove`/`card.redisplay` jobs, payment customer status `review`, and payment attempt card status `review`. Verify the configured connected account before investigating a customer ID. Never resolve an ambiguous customer mapping by assigning an arbitrary provider customer or changing immutable payment consent. Re-run creation reconciliation with the original mapping reference after verifying the account/provider record, or let the buyer use ordinary checkout.

Local coverage: `tests/saved-methods.database.test.ts` verifies consent, lost-response/concurrent creation, web/native session scope, cross-account isolation, removal, immutable fields, provider discrepancies and erasure. `tests/stripe-provider.test.ts` checks the actual SDK's connected-account headers, consent fields, CustomerSession feature grants and detach/redisplay ownership checks with intercepted transport. Real Stripe sandbox/SCA and signed iOS payment-sheet verification remain release evidence.

# Ticket commerce operation

The shared API serves web and iOS. Orders, prices, currency, policies, admission credentials and payment attempts live on the server. External listings return their seller's HTTPS URL and cannot use Clubby stock or checkout. Live commerce remains disabled until the final release gate. No payment test double is available through runtime configuration or HTTP.

## Configure a Stripe sandbox when the account is available

Set `STRIPE_MODE=test`, matching `STRIPE_SECRET_KEY` and `STRIPE_PUBLISHABLE_KEY`, `STRIPE_WEBHOOK_SECRETS` and an allowed `STRIPE_ONBOARDING_ORIGIN`. Store credentials outside Git. The adapter pins Stripe API `2026-08-26.dahlia` and stripe-node 22.6.2. Both clients use the same PaymentIntent, with the connected account passed to Stripe Elements/PaymentSheet. Card payments (including eligible wallet cards) are the initial supported payment method; asynchronous bank-transfer methods are deliberately excluded from the short inventory-hold model.

New sellers use Accounts v2 Merchant configuration, full Stripe Dashboard, and Stripe as fee/loss collector. Stripe collects processing fees from the seller; Clubby requests its exact application fee. The seller is the direct charge account. The application never accepts bank or identity documents itself. Account creation uses a persisted idempotency key; ambiguous creation beyond 23 hours needs provider reconciliation instead of risking a second account. Onboarding links are returned only to the authorized owner, never mailed. A return from onboarding does not activate sales; the backend fetches current capabilities.

An admin creates versioned commercial terms with commission, self-service refund cutoff, commission-refund behavior and seller tax registration. The organization owner must accept the current version. Configure published products, explicitly enable the market, and release the global new-sales pause. Checkout also requires a reviewed organization and a current ready provider account. Test settings are not production terms or tax advice. Fiscal invoices remain the seller's obligation; Clubby exposes a booking receipt and scoped accounting statement.

## Webhooks and workers

Route Stripe snapshot events and Accounts v2 thin account notifications to `POST /v1/webhooks/stripe`. Configure connected-account payment-intent, refund, charge-refunded, dispute, payout and balance events, account capability/requirement changes, and platform payout/balance events. Set the correct endpoint signing secret(s); comma-separated secrets support overlap during rotation. The handler verifies exact bytes, a five-minute signature window and environment, then stores an inbox reference transactionally. It fetches the authoritative provider object in a worker; callback fields cannot grant admission.

Run the worker alongside the API. Maintenance synchronizes pending payments/refunds, expires holds, refreshes capabilities, retries cancellation compensation and reconciles seller/platform balances. Provider requests happen outside database transactions. Worker leases and database effects are fenced, and provider mutations use stable idempotency keys. Failed jobs retain generic errors and bounded retry history; operators must inspect dead jobs and reconciliation `review` results. Do not reset financial idempotency keys to make an error disappear.

Stock locks the occurrence before reading commitments. Tier/event capacity and staff blocks share that lock. Unpaid holds expire after ten minutes. Once payment creation has begun, inventory stays reserved until Stripe proves cancellation or success. Expiry never guesses that a timeout means no payment. A late success during cancellation is recorded and refunded, with admission blocked throughout. Quotes reuse pricing inside a transaction that rolls back completely and explicitly return `reserved=false`.

## Refunds, disputes and reconciliation

One credential is issued for every purchased admission; included drinks have separate redemption counts. Staff scan in their assigned venue/event; only a manager/owner can use a reasoned manual admission override, which still cannot bypass refund/cancellation/dispute state. Retrying a lost scan response must reuse the same idempotency key.

Refunds select explicit, unused, untransferred admission units. Pending refunds disable those rights; only confirmed provider success releases stock and posts the reversal. Exact allocated application fees are refunded separately with another stable key. A failed fee refund remains a visible outstanding job rather than changing the successful customer refund. Event cancellation blocks admission immediately and queues booking impact/refunds. Rescheduling preserves the original purchase snapshot, exposes the current schedule, and notifies buyers.

Refunds performed in the seller's Stripe Dashboard are discovered through callbacks and balance reconciliation. They place the booking into review until authorized staff allocate the exact refunded amount to admissions through `seller/external-refunds/:id/allocate`. No guessed allocation or additional refund is submitted. An arbitrary partial monetary adjustment that does not equal admission units stays in review for a documented accounting/rights decision. A replay of the original successful payment cannot lift that review. Disputes block affected rights until authoritative resolution; payout failures and evidence deadlines remain visible in finance responses and Stripe's seller Dashboard.

Commerce journals explain captured gross sales, seller share, Clubby commission and refund reversals. Provider journals separately record actual balance transactions and fees. Both are balanced and immutable; journals are sealed after the creating transaction. These are separate books, not amounts to add together. Reconciliation compares imported net transactions to available plus pending provider balances and reports discrepancies; it never manufactures a balancing entry. Moving provider balances during pagination can require a subsequent reconciliation. Statements separate currencies.

For a lost payment response beyond the automatic creation window, an authorized finance member can submit the provider PaymentIntent ID to `seller/orders/:id/reconcile`. The service retrieves it from the order's seller account and verifies the immutable order, attempt, amount, currency, fee and environment before recovery. This endpoint cannot create a charge. Customer retrieval remains available after venue hiding or a later change to external commercial mode.

## Client and release checks

The Expo consumer includes ticket selection, terms acceptance, Stripe Elements on web, native PaymentSheet, booking recovery/polling, individual QR display, refund requests and a staff camera scanner. Only current server state grants admission. Permission denial/offline scanning never produces an accepted result. Apple Pay additionally requires a real merchant identifier, native signing entitlements and platform/domain registration. Configure the identifier in both Expo build plugin and runtime; no identifier is invented in source.

Local tests use real PostgreSQL, actual HTTP signature verification and the real Stripe SDK with intercepted network transport. They do not claim a Stripe-hosted sandbox payment, device camera test, 3-D Secure challenge, Apple Pay authorization or signed App Store build. Those must run with the user-configured accounts before release. Record successful, declined, challenged, interrupted and webhook-delayed payments on both clients.

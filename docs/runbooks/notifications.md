# Notifications and delivery operations

Booking confirmations, refunds, table receipts, group state changes, invitations, seller reviews, event changes and reminders are committed with domain changes. Migration 010 publishes each notification to a durable outbox. Email acceptance, provider delivery feedback, in-app reads and APNs attempts are separate records; an accepted API request is not proof that an email reached a mailbox.

`/v1/me/preferences` uses an expected version to prevent one device overwriting another. Marketing defaults off and changes are audited. Booking email and push are independently optional. Sign-in messages are essential email and excluded from the account inbox. Permanent bounces and complaints suppress all mail to that address, including sign-in, until an administrator verifies the mailbox and records a reason for release. Never release a complaint without the recipient's consent. Support can inspect delivery states without reading message content.

Email configuration: `EMAIL_MODE=resend`, verified `EMAIL_FROM`, secret `RESEND_API_KEY`, and comma-separated `RESEND_WEBHOOK_SECRETS` for key rotation. Subscribe the signed HTTPS `/v1/webhooks/resend` endpoint to sent, delivered, delayed, bounced, complained, failed and suppressed events. Verification uses the original raw body and Svix timestamp/signature checks before parsing. Duplicate IDs with different signed payloads are rejected. Events arriving before the send receipt are reconciled. Older acceptance/delay events cannot erase delivery or rejection evidence. Beyond Resend's idempotency window, delivery stops for review rather than risking duplicate messages.

Push uses APNs directly, without forwarding personal data to the Expo Push Service. Mount the Apple `.p8` private key and set `APPLE_PUSH_ENABLED=true`, `APPLE_TEAM_ID`, `APPLE_PUSH_KEY_ID`, `APPLE_PUSH_KEY_PATH`, `APPLE_PUSH_BUNDLE_ID` and `APPLE_PUSH_ENVIRONMENT`. Match the native build's `EXPO_PUBLIC_APNS_ENVIRONMENT` to its signed entitlement. TestFlight and App Store builds use production APNs. The web client uses the same inbox and preferences; web push is not enabled.

An iPhone asks for permission only when the person selects Enable notifications. Tokens are encrypted and scoped to a current authenticated session. Logout/revocation cancels pending delivery, account switching replaces the installation binding, and removing a device requires explicit re-enabling. Rotated or unregistered tokens cannot inherit old queued notifications. Push payloads contain a generic alert and opaque notification ID; opening it retrieves an authorized notification before following a typed target. Booking and ticket APIs independently check current ownership. Denying permission leaves email and the inbox available. Logout also clears presented local notifications.

Chat notifications contain no message content, are limited to one per recipient/group/five-minute bucket, exclude blocked authors, and recheck membership before push. Event reminders cover the next 1–24 hours, use the occurrence timezone, deduplicate by current holder/event/schedule, and suppress cancelled or inactive admissions before delivery. Cancellation/reschedule notices also reach transferred ticket holders; refunds remain with their original payers.

Validation: `tests/notifications.database.test.ts` exercises real PostgreSQL, signed raw HTTP feedback, consent races, deduplication, recipient isolation, session revocation, device reassignment, group scope and transferred reminders. `tests/push-provider.test.ts` verifies ES256 credentials and HTTP/2 request/payload/error behavior against a local protocol endpoint. Both client bundles must export. These do not replace signed-iPhone delivery/permission/background tests or a verified Resend domain; those require the accounts the user will configure later.

# Ticket transfers and wallet passes

Transfers move an unused admission and its remaining vouchers, never the buyer's payment, receipt, group contribution or seller obligation. A registered, verified owner invites one email; that email must be verified on the accepting account. Acceptance records the terms, locks occurrence/order/ticket in the same order as scans and refunds, changes the owner and rotates the QR. Invitations expire after 48 hours or at event start, whichever comes first. Pending invitations do not freeze admission: a successful scan or refund prevents acceptance. Revoke an invitation from Tickets. A recipient can transfer it back to the buyer for an ordinary self-service refund. Table invitations explicitly preserve the buyer/group owner's whole-reservation cancellation right; used admissions still prevent self-service cancellation. Invitations are limited and respect recipient blocks.

The Tickets view includes received admissions without granting access to another purchaser's order, support messages, receipt or payment secrets. QR values are absent from transfer audit/idempotency records and invitation tokens are encrypted at rest.

## Activate wallets

Apple: mount the pass certificate, its private key and the matching Apple WWDR certificate outside the repository. Set `APPLE_WALLET_ENABLED=true`, `APPLE_PASS_TYPE_ID`, `APPLE_TEAM_ID`, `APPLE_PASS_CERT_PATH`, `APPLE_PASS_KEY_PATH`, `APPLE_WWDR_CERT_PATH` and optional `APPLE_PASS_KEY_PASSPHRASE`. `PUBLIC_API_URL` must be HTTPS and accessible to Wallet. These are pass credentials, separate from Apple Pay merchant credentials. Renew certificates before expiry and preserve existing pass type/team IDs and encrypted authentication tokens.

Google: configure an approved Google Wallet issuer/service account, grant issuer access, mount its PKCS#8 RSA key and set `GOOGLE_WALLET_ENABLED=true`, `GOOGLE_WALLET_ISSUER_ID`, `GOOGLE_WALLET_CLIENT_EMAIL`, `GOOGLE_WALLET_KEY_PATH`. Complete real venue addresses before issuing event passes. Provider review/publishing access and actual account/device verification remain deployment acceptance requirements.

No wallet is advertised until its provider is configured. Customer-authorized generation produces an Apple download link lasting two minutes and consumed once, or a Google save JWT lasting five minutes. The Apple link is tied to a live session and current ticket ownership; HEAD does not consume it. No API session token is embedded in the link. Browser/native clients open the signed download through the operating system; Google save is available on the website.

Each ticket credential version gets a distinct pass serial and Google object/class. Existing serial authentication never changes. A prior holder's pass becomes void, with no barcode or replacement owner's credential. Installed passes use Apple's specified pass authorization, registration, update-list, update-download and unregister routes under `/v1/wallet/apple`. Device identifiers are hashed; push tokens are encrypted. Updates use an opaque snapshot digest, avoiding sequence/commit-order cursor gaps. Device logs are acknowledged without storing their potentially sensitive payload.

Database triggers mark passes dirty after ticket, booking, schedule, table balance and account-state changes. Workers enqueue durable `wallet.sync` jobs; provider failures retry through the existing outbox. APNs uses the pass certificate and production APNs endpoint, with an empty update payload. Invalid device tokens are removed; transient failures remain retryable. Google objects are patched from authoritative state. Periodic resynchronization repairs delayed/out-of-order provider updates; installed wallet presentation is eventually consistent. Admission always consults the authoritative online backend, so a stale pass cannot bypass refund, transfer, dispute, balance or redemption rules. Expiration is also encoded in both pass formats.

Monitor dead `wallet.sync` jobs and certificate/issuer failures through the operational queue. Requeue only after correcting configuration or provider availability. Do not rotate pass authentication tokens as a retry mechanism. A customer can always retrieve their current ticket in Clubby when a wallet provider is unavailable.

## Local verification

`tests/transfers.database.test.ts` covers verified recipient scope, expiration/revocation, return transfers, whole-table cancellation and real PostgreSQL transfer/refund/scan races. `tests/wallet.database.test.ts` covers session-bound downloads, wallet protocol authorization, registration/update cursors, version isolation, state changes and retry behavior. `tests/wallet-provider.test.ts` verifies the generated manifest and detached CMS signature with an ephemeral test certificate, plus Google OAuth/save signatures and REST requests with intercepted transport. Test certificates are not Apple-trusted and do not establish live provider/device acceptance.

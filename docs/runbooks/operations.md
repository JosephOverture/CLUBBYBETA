# Operational recovery

The administrator **Operations** screen reads `/v1/admin/operations` and paginated jobs. It exposes counts and safe job metadata, never payloads, payment secrets, email bodies or credentials. A worker independently renews its heartbeat every ten seconds and reports successful maintenance. `/health/live` and `/health/ready` on worker port 4101 are private container checks; never expose this port through the public load balancer.

The worker writes one structured `operations.snapshot` each successful maintenance minute. Terraform configures queue-age, dead-job, expired-lease, financial-review, deletion-overdue and missing-worker alarms, API 5xx and database-space alarms, a dashboard and encrypted SNS delivery. Confirm the operator subscription and trigger a real staging alarm before release. Local metric generation does not prove notification delivery. Do not put customer data in alert messages.

On alert, identify the affected resource in Support, Finance, Privacy or Operations. Correlate request IDs from `x-request-id`, order IDs, provider object IDs and immutable audit entries. Check the earliest failure and provider dashboard before initiating recovery. A queue age above five minutes, missing snapshots for three minutes, failed refunds or an overdue deletion requires an operator. Pause new sales through Administration if paid fulfilment or admission integrity is at risk; existing bookings and refunds remain accessible.

Jobs use 30-second leases, renew every ten seconds and fence completion by lease ownership. An old worker cannot record completion after losing its lease. External effects still require their domain idempotency: a process may disappear after a provider accepts a request but before its receipt is committed. Never infer payment failure from a timeout.

The generic replay command accepts only explicitly allowed nonfinancial topics, a current replay generation, recent administrator authentication and an audit reason. Concurrent/repeated replay is rejected. Payment/refund work must use scoped Support/Finance reconciliation; email delivery beyond the provider idempotency window needs delivery review; privacy uses its request-version recovery command. Do not reset financial job attempts in SQL or delete receipts to force a retry.

For provider outage, pause affected new sales, retain webhook inbox/outbox records, leave ambiguous attempts pending and use the provider-object reconciliation workflow after recovery. For a worker crash, replace the task and inspect expired leases; receipts and durable job IDs survive replacement. For a database outage, APIs fail readiness and no local in-memory sale becomes authoritative. Restore database availability before restarting workers. For compromised staff credentials, revoke sessions and memberships, inspect audit history and freeze affected seller actions. Existing runbooks for commerce, tables, groups, notifications, privacy and tickets define the domain-specific compensation paths.

## Restore rehearsal and production recovery

`tests/operations-rehearsal.database.test.ts` uses a disposable PostgreSQL database, 40 competing buyers, 20 paid test orders and concurrent admission scans. It runs real `pg_dump` and `pg_restore`, compares row counts and content fingerprints for every public table, then reclaims a stranded job and checks one effect. The test writes only aggregate timing evidence to `.local-data/evidence/operations-rehearsal.json`. Install PostgreSQL 17 command-line tools and set `PG_BIN_DIR`; Windows defaults to `.local-data/pg-tools`. The embedded server package itself does not contain backup tools. The CLI archive used locally comes from [PostgreSQL's linked Windows binary distributor](https://www.enterprisedb.com/download-postgresql-binaries). Tests never drop the supplied database; they create and remove their own uniquely named databases.

Production targets remain RPO 15 minutes and RTO four hours until measured against the actual deployment and agreed venue load. RDS is private, encrypted, protected against deletion and configured for 35-day point-in-time recovery. Monitor its latest restorable time and rehearse a restore into a separate isolated database at least quarterly and after material schema changes. A tiny local logical restore does not establish the production targets.

For a real restore: stop new sales and workers; preserve the failed system and incident timestamps; restore to a new private RDS instance; verify the environment, migration checksums, table counts and financial totals; reconcile every Stripe payment/refund/dispute since the recovery point from provider truth; apply the separately retained privacy-erasure incident journal so deleted users are not resurrected; invalidate restored sessions and device delivery registrations; replay only through domain recovery; verify sample tickets and ledger balances; switch the database secret; start workers, then APIs, and reopen sales only after operator review. Keep the old database isolated until the incident review closes. Media deletion is final: the private media bucket deliberately does not retain object versions. Missing erased media after database recovery must stay unavailable.

For deployment rollback, restore the previous image/task definitions without running old migrations. All deployment migrations must remain additive until the previous artifact's support window closes. API readiness accepts additional applied migrations while checking every migration known to its own artifact. The first upgrade from a pre-M8 artifact requires a maintenance window because the earlier readiness check required an exact migration count. The deployment script verifies migration exit status, service adoption and public readiness; a failed rollout restores prior task definitions and reports failure. Rehearse that workflow in staging; its cloud execution is not a local test result.

## Encryption and provider-secret rotation

`APP_ENCRYPTION_KEY` is the write key; `APP_ENCRYPTION_PREVIOUS_KEYS` is a comma-separated overlap ring of at most two additional 32-byte hex keys. Keys never belong in source, task environment overrides, terminal arguments, logs or Terraform state. Use Secrets Manager values and deploy new tasks when a secret changes. Retain historical keys in restricted recovery escrow until every backup encrypted with them has expired.

For routine rotation, first deploy all readers with the old write key and the new key in the overlap ring. Then deploy the new write key with the old key in the overlap ring. Verify both task generations can read both formats. Drain APIs and workers, verify a backup, wait for worker heartbeats to expire and run the maintenance command `rotate-encryption` using the current application task definition with `ROTATION_MAINTENANCE_ACK=services-drained-and-backup-verified`. It takes ordered exclusive table locks, authenticates every encrypted field, rewraps in one transaction and records an audit event. Any corrupt/unknown-key record aborts the transaction. Rerunning with the same active key changes zero records. Resume with the new key, validate sessions, tickets and provider receipts, then remove the old key from online tasks. Do not retire recovery keys simply because the active database has been rewrapped. A suspected key compromise also requires revoking exposed session/ticket/provider credentials; re-encryption alone does not undo disclosure.

Rotate Stripe and Resend webhook secrets with an overlap period using their configured comma-separated secret lists. Rotate API/provider signing credentials separately, validate staging delivery or verification, deploy all tasks, then revoke the old credential. The AWS SDK uses the task role for S3, avoiding long-lived access keys. Database login rotation requires updating the corresponding database role and secret together and draining/replacing pooled connections.

References: [node-postgres TLS configuration](https://node-postgres.com/features/ssl), [ECS task IAM roles](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-iam-roles.html), [CloudWatch alarms and encrypted SNS topics](https://repost.aws/knowledge-center/cloudwatch-configure-alarm-sns). RDS URL TLS overrides are rejected and the verified CA is supplied separately so the connection string cannot silently replace certificate validation.

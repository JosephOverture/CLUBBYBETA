# Engineering decisions and commercial gates

Recorded 2026-09-23 against prototype e121114 and the unversioned local Clubby scaffold.

1. **Repository:** Project-Clubby is the implementation repository. Preserve the root HTML prototype byte-for-byte. Do not modify the neighboring Clubby project or migrate its `.local-data`, credentials, or generated dependencies. Use reviewed concepts/tests selectively; record ID mappings before any later data import.
2. **One backend:** NestJS/TypeScript with PostgreSQL transactions, database outbox, independent worker, `/v1` contracts and a shared client SDK. Web and iOS use the same customer, inventory and financial records. Client headers never establish identity or business authority.
3. **Commercial model — confirmed by user:** venues/organizers are sellers; Clubby takes a commission. Some listings instead redirect to another company's checkout (for example Eventbrite). External purchases are not Clubby orders and cannot be granted Clubby admission. A switch to external mode affects new purchases only.
4. **Provider:** Stripe Connect is the selected integration target. Account creation/connection happens later at the user's request. No actual provider account or live payment readiness is claimed. Charge type, processing-fee bearer, commission schedule, chargeback allocation, refund rules and payout delay require explicit, versioned commercial configuration before native sales. Absence must deny sales, never invent terms.
5. **Environments — confirmed by user:** no external accounts are configured; prepare deployment locally. Local executable checks replace cloud provisioning for the current engineering gates. Real provider tests, staging/device evidence and live deployment remain M8 release requirements, not fabricated successes.
6. **Identity:** shared customer IDs and independently revocable web/native sessions; email verification and optional OIDC/Apple adapters. Local delivery sink is development-only, never an alternate public identity issuer. Verify account linking independently; matching email alone cannot link identities. Web HttpOnly cookies with origin/CSRF checks; native refresh secrets in OS secure storage.
7. **Markets:** Milan/EUR for launch. Store full timestamps and IANA timezone, immutable order currency and minor-unit amounts. Browsing enablement and native payment enablement are separate. Geography extensions belong to M3, not the platform migration.
8. **Client structure:** retain current prototype as product reference. Add minimal iOS/web development consumers of the same SDK for foundation verification. M24 requires replacing simulated product interactions, not just compiling these development consumers. No iOS signing is possible without the owner's Apple/cloud-build setup.
9. **Compatibility:** additive v1 evolution. Preserve every released v1 contract until a separately reviewed deprecation window and working customer recovery path exist. There is no released signed app baseline yet; the initial SDK response fixtures are the first compatibility baseline.
10. **Policies:** one credential per admission, online authoritative redemption, occurrence-specific table inventory. No commercial defaults inferred from demo 20% or 20:00 strings. Require approved offer policies for deposits, cancellation, group expiry, unpaid balance liability and excess-payment/refund handling. Taxes and invoice rules are configured with the seller's business inputs; code does not supply legal conclusions.
11. **Data:** no personal data in ordinary request logs, job errors or public projections. Separate operational data from retained financial/audit records. Approved retention schedules and privacy copy gate production. Development fixtures are labeled and never automatically inserted into production.
12. **Reliability:** short transactions, deterministic lock order, bounded timeouts, no provider requests under database locks. Jobs are at-least-once; handlers need receipts/provider idempotency. Provider success is authoritative, client success redirects are not. Release targets: 99.9% monthly availability, RPO 15 minutes, RTO 4 hours, p95 reads/scans 500ms at a measured agreed peak. These are unverified targets until M8.
13. **Identity implementation refinement:** managed OIDC is supported behind a configured issuer/audience/JWKS boundary; verified email sign-in provides a passwordless path independent of a chosen identity vendor. It uses a random single-use email token bound to the initiating client's verifier. The local sink is replaceable with Resend for delivery; no home-grown password storage is introduced. Provider linking requires an existing verified session and recent authentication. Provider revocation/Apple-specific token lifecycle must be configured and verified before enabling those providers for release.
14. **Geography implementation:** the initial portable PostgreSQL schema uses bounded latitude/longitude, a coordinate index, GIN text/tag indexes, antimeridian-aware viewport filtering and server-calculated great-circle distance. This delivers the planned nearby/map behavior without requiring an unavailable local PostGIS installation. PostGIS remains an optional deployment optimization for measured spatial load, not a second authoritative catalogue. M8 must measure the chosen deployment's query performance.
15. **Media implementation:** authorize exact-size image uploads, keep originals in private storage, re-encode JPEG/PNG/WebP into metadata-stripped WebP variants, then remove originals. Private S3 is the deployed adapter; the file adapter is development-only. Public API delivery verifies current publication/reference state on every request. CDN caching must retain these publication/privacy rules and is a deployment optimization, not an excuse to expose quarantine objects.

16. **Collaboration transport:** group history and state use authenticated cursor-based polling, with five-second foreground refresh and renewed authorization on every request. Reconnect resumes from persisted records. This is the initial realtime implementation; sockets are unnecessary for correctness and would not replace database authority.
17. **Discovery and metrics:** indexed venue text/tag search, distance/viewport queries, deterministic pagination, opening status and administrator-curated featured placements are the retained discovery controls. Availability comes from occurrence inventory endpoints. Unsupported simulated trending, NPS, queue-time and current-occupancy claims are removed. Reports use committed orders, ledger entries and admission records; no speculative analytics collection is added.
18. **Deployment reference:** AWS Frankfurt is the default configurable reference, with separate environment state, private PostgreSQL/Fargate, S3, Secrets Manager, HTTPS ALB/WAF and CloudWatch/SNS. Infrastructure validation and mocked plans are local evidence, not provisioning or delivery evidence. Linux container execution remains a CI gate because Docker is unavailable on this host.
19. **Release boundary:** local phase completion and public-release approval are different gates. `pnpm gate M8` checks recorded local evidence; `pnpm gate M8 --release` also rejects outstanding external obligations. Production live commerce additionally validates a time-bounded, revision/origin-specific approval manifest and independently enforces approved market, seller and offer policies.

No engineering choice approves unconfigured commercial terms. The user explicitly authorized local preparation; phase reports distinguish local evidence from release evidence. The portable geography/media choices above preserve the required backend behavior; CDN caching, PostGIS, websockets, offline admission and web push are optional future optimizations/extensions, not hidden prerequisites for the implemented local system.
